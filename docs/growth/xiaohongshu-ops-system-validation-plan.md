# 小红书运营系统真实商品验证方案

> 阶段：调研后的实证验证。
> 目的：用 3 个真实货源商品验证“选品与内容测试工作台”是否值得进入开发。
> 边界：先用无代码表格和人工执行，不开发、不自动采集、不自动发布。

## 1. 验证目标

这次验证不证明“能不能爆单”，只证明 5 件事：

1. 用户是否愿意按系统录入商品、货源和对标。
2. 系统评分是否能帮用户筛掉不该测的商品。
3. 7 天内容测试计划是否能指导真实执行。
4. 每天数据回填是否能控制在 3 分钟左右。
5. 数据回来后，系统是否能给出比凭感觉更清晰的下一步动作。
6. 用户更愿意购买诊断、陪跑、模板、内部服务，还是自助 SaaS。
7. 哪些 AI 提示词输出稳定可用，哪些需要人工大量修改。

如果这些事情成立，再讨论开发才有意义。

## 2. 验证对象

优先选择这一类用户：

**有货源、想做小红书、但缺选品判断和内容测试方法的小商家。**

进入 7 天验证前，建议先用
`docs/growth/xiaohongshu-ops-system-user-interview-guide.md`
完成 3 个目标用户访谈。只有当受访者有真实商品、愿意补 3 条对标、愿意每天 3 分钟回填数据时，才进入真实商品验证。

不要一开始找：

- 纯小红书内容博主。
- 没有任何货源的新手。
- 大品牌市场部。
- 成熟代运营团队。
- 需要复杂投放和多人审批的团队。

原因：第一版系统的核心不是教学，也不是投放管理，而是把现有货源翻译成小红书测试动作。

## 3. 商品选择标准

一轮验证选 3 个真实商品，最好覆盖三种风险/机会类型：

| 商品类型 | 目的 | 示例 |
| --- | --- | --- |
| 低风险测试品 | 验证流程是否跑得顺 | 手工材料、收纳小物、小家居配件 |
| 内容场景强商品 | 验证 AI 和模板是否能生成测试方案 | 礼物、情绪陪伴、桌面小物 |
| 风险识别商品 | 验证系统能否劝退或要求补证据 | 大件、服鞋、IP 周边、功效表达商品 |

每个商品必须满足：

| 条件 | 最低要求 |
| --- | --- |
| 有真实货源 | 能提供成本、起订量、发货方式 |
| 有明确售价参考 | 小红书或同类平台能找到价格区间 |
| 有毛利空间 | 预估毛利率最好不低于 35% |
| 有内容场景 | 至少能想出 3 个使用/赠送/情绪/身份场景 |
| 有对标样本 | 至少能找到 3 条小红书对标 |
| 风险可控 | 不涉及明显侵权、医疗功效、虚假承诺 |

如果某商品找不到 3 条对标，不进入 7 天测试，只进入“补证据”状态。

## 4. 验证节奏

建议总周期 10 天：

```text
Day -2 到 Day 0：建表、选品、补对标、生成内容计划
Day 1 到 Day 7：发布或模拟发布，逐日回填数据
Day 8：总复盘，判断是否值得开发
```

### Day -2：选商品

动作：

- 从真实货源里选 5-10 个候选。
- 用 `Products` 表快速录入成本、售价、类目、场景、风险。
- 初筛出 3 个验证商品。

产出：

- 3 个商品进入验证。
- 其他商品进入“观察/补证据/放弃”。

通过标准：

- 每个商品录入不超过 15 分钟。
- 录入后能给出初步下一步动作。

### Day -1：补对标和供应链

动作：

- 每个商品补 3 条对标。
- 每个商品至少补 1 个供应商证据。
- 记录成本、发货、退换货、破损、售后风险。

产出：

- 9 条以上对标样本。
- 3 条以上供应链记录。

通过标准：

- 对标能支撑选品评分。
- 供应链风险能进入扣分项。

### Day 0：生成 7 天内容计划

动作：

- 每个商品生成 9 条内容方案。
- 每个商品至少覆盖 3 个场景。
- 商品笔记和普通笔记混合。
- 做发布前规则检查。

产出：

- 每个商品 9 条 `ContentPlans`。
- 每个商品 7 天 `Publishing` 排期。

通过标准：

- 内容方案能直接指导拍摄、制图或写文。
- 高风险表达被识别并改写。

### Day 1-2：小样本启动

动作：

- 每天发布或模拟发布 2-3 条。
- 记录 24 小时数据。
- 不急着改方向，先积累基础信号。

重点看：

- 曝光是否极低。
- 收藏/评论是否出现。
- 是否有人问价格、材质、尺寸、适用人群。
- 是否有明显规则或售后风险。

### Day 3-4：保留有效方向

动作：

- 停掉完全无信号方向。
- 对有信号的封面/标题做变体。
- 把评论问题转成新内容。
- 检查价格、详情页、商品图、评论区信任状。

重点看：

- 哪个场景最有反应。
- 加购是否出现。
- 评论疑虑集中在哪。
- 是否需要换封面、换标题、换价格或换供应链。

### Day 5-7：放大或放弃

动作：

- 对有加购/成交的方向加密内容。
- 对有互动无成交的方向补信任和详情。
- 对无信号商品停止测试。
- 对售后风险商品暂停放大。

产出：

- 每个商品一个明确结论。
- 每个商品一个下一步动作。

可选结论：

- 放大。
- 换封面。
- 换标题。
- 换场景。
- 换价格。
- 换供应链。
- 补证据。
- 放弃。

### Day 8：总复盘

动作：

- 汇总 3 个商品表现。
- 复盘字段是否太重。
- 复盘 AI 生成内容是否可用。
- 复盘哪些提示词值得后续产品化。
- 复盘用户是否愿意持续填。
- 复盘用户更认可哪种付费形态。
- 判断是否进入开发讨论。

产出：

- 一份验证报告。
- 一个开发/不开发建议。

## 5. 数据回填字段

每天只回填最小字段，不要把表格做成负担。

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| 日期 | 是 | 记录测试周期 |
| 商品 | 是 | 关联 Products |
| 笔记/内容方案 | 是 | 关联 ContentPlans |
| 发布状态 | 是 | 已发 / 未发 / 模拟 |
| 曝光 | 是 | 判断基础流量 |
| 点赞 | 是 | 互动信号 |
| 收藏 | 是 | 兴趣信号 |
| 评论 | 是 | 需求和疑虑 |
| 加购 | 强烈建议 | 最接近购买意图 |
| 成交 | 强烈建议 | 经营结果 |
| 评论关键词 | 是 | 生成下一批内容 |
| 退货/售后信号 | 是 | 风险判断 |
| 复盘结论 | 是 | 下一步动作 |

回填时间目标：每天 3 分钟以内。

如果做不到，说明字段太重，需要删字段，而不是急着开发自动化。

## 6. 判断阈值

这不是绝对算法，只是第一轮验证用的决策规则。

| 信号 | 判断 | 下一步 |
| --- | --- | --- |
| 3 条内容完全无曝光/互动 | 商品或内容方向弱 | 换封面/标题，最多再试 2 条 |
| 有收藏无加购 | 场景有兴趣，商品价值不清晰 | 补使用场景和商品细节 |
| 有评论问价格/尺寸/材质 | 需求存在 | 补详情页、评论区和对应笔记 |
| 有加购无成交 | 价格、信任或详情问题 | 查价格带、评价、详情图、运费 |
| 有成交且售后风险低 | 可以小幅放大 | 增加同方向内容 |
| 有成交但退货/差评风险高 | 暂停放大 | 换供应链或改预期管理 |
| 规则风险被命中 | 不进入发布 | 改写、降风险或放弃 |

## 7. 成功标准

验证通过不要求 3 个商品都卖爆。

满足下面 4 条，就可以进入开发讨论：

1. 至少 2 个商品能在 15 分钟内完成录入。
2. 至少 2 个商品能找到 3 条以上有效对标。
3. 至少 1 个商品的 7 天测试计划能被用户认为“可直接执行”。
4. 数据回填后，用户认可系统给出的下一步动作比自己凭感觉更清晰。

如果出现真实成交，是加分项，不是唯一判断。

## 8. 失败标准

出现任意 2 条，就不建议开发：

1. 用户不愿意录入成本、售价、货源和对标。
2. 用户只想要文案，不愿意做测试和复盘。
3. 内容方案无法指导真实拍摄或发布。
4. 每天回填明显超过 5 分钟。
5. 数据回来后仍然无法给出下一步动作。
6. 规则风险太高，很多内容不能安全发布。
7. 真实商品找不到有效对标，评分模型无法工作。

失败不是坏事。它说明系统边界还没找准，应该继续缩小范围。

## 9. 用户访谈问题

验证结束后问用户这些问题：

1. 录入商品时，哪些字段最烦？
2. 哪些字段让你觉得“确实有用”？
3. 选品评分有没有改变你原来的判断？
4. 对标拆解有没有帮你看懂别人为什么能卖？
5. 9 条内容方案里，有几条你愿意真的发？
6. 7 天排期会让你更想执行，还是觉得压力大？
7. 每天回填数据是否能坚持？
8. 系统给的下一步动作是否清楚？
9. 你最希望 AI 帮你做哪一步？
10. 你最担心这个系统误导你什么？

访谈比成交更重要。因为当前阶段要验证的是“系统是否改变操盘方式”，不是单品爆发概率。

## 10. 验证报告模板

每轮验证结束后，写一页报告：

| 项目 | 内容 |
| --- | --- |
| 验证日期 | 起止时间 |
| 验证用户 | 用户类型、货源情况、账号阶段 |
| 商品 1 | 名称、评分、结论、下一步 |
| 商品 2 | 名称、评分、结论、下一步 |
| 商品 3 | 名称、评分、结论、下一步 |
| 最有用字段 | 用户明确觉得有帮助的字段 |
| 最重字段 | 用户觉得麻烦或不会填的字段 |
| AI 可用性 | 哪些 AI 输出能直接用 |
| 提示词表现 | 哪些 Prompt ID 可用、哪些需要重写 |
| 规则风险 | 命中的主要风险 |
| 商业化信号 | 更适合买诊断、陪跑、模板、内部后台还是 SaaS |
| 是否建议开发 | 是 / 否 / 继续无代码验证 |
| 原因 | 3 条以内 |

## 11. 开发讨论门槛

验证时先按 `docs/growth/xiaohongshu-ops-system-mvp-prd.md` 的 P0 范围执行，不临时扩到自动采集、自动发布、开放平台 API 或服务市场上架。

只有当验证报告满足这些条件，才进入开发讨论：

| 门槛 | 要求 |
| --- | --- |
| 用户愿意填 | 关键字段不被认为过重 |
| 商品能筛选 | 系统能让用户放弃或推迟至少 1 个不合适商品 |
| 内容能执行 | 至少 1 个商品的内容包被真实采用 |
| 复盘能决策 | 数据回填后有明确下一步 |
| 风险能提醒 | 至少识别出 1 个真实发布风险 |
| 用户强匹配 | 至少 3 个目标用户访谈，且至少 1 个强匹配用户愿意进入验证 |
| 付费形态清楚 | 能判断下一步应先卖诊断、陪跑、模板、内部后台还是 SaaS |
| AI 能力可验证 | 至少 2 个提示词在真实商品里输出可用，并记录人工修改点 |
| 平台边界清楚 | 明确第一版是否仍坚持手动录入/截图证据，不依赖开放平台接口或服务市场上架 |

如果这些都成立，开发优先级就是：

1. 商品录入和选品评分。
2. 对标拆解。
3. 7 天内容测试计划。
4. 数据回填和复盘结论。
5. 规则风险提醒。

仍然不要先做自动发布。

也不要把开放平台 API、服务市场上架、浏览器插件或自动采集作为第一轮开发前提。它们只适合放在验证通过后的后续路线里。
