## 1. MVP 一句话定义

MVP 不是小红书 AI 文案工具，也不是数据平台。

MVP 是：

**帮有货源的小商家，把 3 个真实商品跑完“选品判断 -> 对标拆解 -> 内容测试 -> 数据回填 -> 下一步动作”的轻量工作台。**

第一轮形态优先是飞书多维表格或 Notion，不开发。

## 2. 目标用户

只服务这一类人：

| 用户 | 必须满足 | 不满足则不进入验证 |
| --- | --- | --- |
| 有货源的小商家 | 有真实商品、成本、供应链、发货能力 | 只有想法，没有货源 |
| 想做小红书电商 | 愿意找对标、做内容、看数据 | 只想找人代运营 |
| 能每天配合 3 分钟 | 愿意回填曝光、互动、加购、成交、评论疑虑 | 不愿意记录数据 |
| 可接受人工流程 | 愿意先用表格和截图验证 | 一上来要求自动化 |

第一批不要服务：品牌市场部、成熟代运营团队、纯内容博主、没有货源的新手。

## 3. 核心问题

MVP 只回答 5 个问题：

1. 这个商品值不值得测？
2. 它的小红书对标是谁？
3. 第一批内容应该从哪些场景切入？
4. 数据回来后下一步是放大、调整、补证据、暂停还是放弃？
5. 过程中有什么规则、供应链或表达风险？

不回答：

- 怎么自动采集全网数据。
- 怎么自动发笔记。
- 怎么自动挂车。
- 怎么替代千帆后台。
- 怎么保证合规。
- 怎么直接做服务市场应用。

## 4. P0 范围

P0 只做 6 个模块。

| 模块 | 目标 | 最小能力 | 验收标准 |
| --- | --- | --- | --- |
| 商品候选库 | 判断商品能不能测 | 录入成本、售价、毛利、场景、风险、状态 | 至少 3 个商品完整录入 |
| 供应链记录 | 判断能不能承接流量 | 记录货源、起订、发货、退货、质量风险 | 每个入选商品至少 1 个供应商证据 |
| 对标库 | 防止 AI 空写 | 记录 3 条对标链接/截图/标题/封面/销量或加购证据 | 至少 2 个商品各有 3 条有效对标 |
| 内容测试计划 | 把商品转成可执行内容 | 每个商品生成 3 个场景、9 条内容方向 | 至少 1 个商品内容包被用户认为可执行 |
| 数据回填 | 形成复盘闭环 | 每天记录曝光、互动、收藏、加购、成交、评论疑虑 | 每天回填不超过 3 分钟 |
| 下一步动作 | 体现系统价值 | 输出放大/调整/补证据/暂停/放弃 | 至少形成 1 次真实经营动作 |

## 5. P1 范围

P1 可以做，但不影响第一轮验证成立。

| 模块 | 为什么是 P1 | 什么时候做 |
| --- | --- | --- |
| 模板库 | 有价值，但容易变成照抄模板 | P0 流程跑通后沉淀 |
| 规则库 | 必须有字段，但第一轮可手动记录 | 真实发布前补强 |
| AI 复盘 | 有价值，但需要真实数据 | 有 3-7 天回填后 |
| 用户访谈评分 | 决定商业化包装 | 3 个目标用户访谈后 |
| 商业化方案 | 不应早于价值验证 | 用户认可下一步动作后 |

## 6. 明确不做

第一轮明确不做：

| 不做 | 原因 |
| --- | --- |
| 自动发布 | 账号、平台规则、责任边界都不适合早期处理 |
| 自动采集 | 权限、稳定性、合规成本高，且不是验证重点 |
| 自动挂车 | 需要千帆后台规则和账号权限，不做 MVP 前提 |
| 自动判定合规 | 系统只能提醒风险，不能替代官方规则 |
| 浏览器插件 | 会把验证焦点带到技术复杂度 |
| 开放平台 API 接入 | 接口权限和服务商规则未验证 |
| 服务市场上架 | 入驻、审核、服务、合规成本过早 |
| 大而全数据看板 | 竞品已很强，且不解决下一步动作 |

## 7. 用户故事与验收

### 7.1 商品录入

作为有货源的小商家，我想把商品成本、售价、供应商和发货方式录进去，这样我能先判断它是不是值得做小红书测试。

验收：

- 能算出预估毛利。
- 能标出履约风险和规则风险。
- 能给出下一步：补证据 / 找对标 / 做内容 / 放弃。

### 7.2 对标拆解

作为运营者，我想保存 3 条小红书对标笔记或商品链接，这样 AI 和人都不会凭空写内容。

验收：

- 每条对标有链接或截图。
- 能记录标题结构、封面结构、场景、销量/加购证据。
- 能标出可借鉴点和不可照抄点。

### 7.3 内容测试

作为商家，我想为一个商品生成 9 条不同角度的测试内容，而不是 9 条差不多的标题。

验收：

- 至少 3 个场景方向。
- 至少 1 条商品笔记方向。
- 至少 1 条普通笔记方向。
- 每条内容有标题、封面方向、正文结构和风险标签。

### 7.4 数据复盘

作为商家，我想每天只填少量数据，但最后能知道下一步该干什么。

验收：

- 回填字段不超过 8 个核心字段。
- 能根据数据输出明确动作。
- 不能只有“继续优化”这种空话。

## 8. 最小数据模型

第一轮只需要 6 张 P0 表：

| 表 | 必须字段 |
| --- | --- |
| `Products` | 商品名、包装名、成本、售价、毛利、状态、评分、下一步动作 |
| `Suppliers` | 供应商、链接、成本、发货、退货、质量风险 |
| `Benchmarks` | 对标链接、截图、标题、封面、数据证据、可迁移点 |
| `ContentPlans` | 场景、标题、封面、正文结构、风险、状态 |
| `Publishing` | 账号、发布时间、链接、是否挂车、发布状态 |
| `Metrics` | 曝光、点赞、收藏、评论、加购、成交、退货、疑虑 |

`Templates` 和 `Rules` 可以先作为轻量辅助表，不阻塞第一轮验证。

## 9. AI 放哪里

AI 只做 4 件事：

| AI 能力 | 输入 | 输出 | 禁止 |
| --- | --- | --- | --- |
| 商品理解 | 商品资料、供应链、售价 | 人群、场景、风险、缺证据 | 不编造销量和成本 |
| 对标拆解 | 对标链接摘要、截图描述、标题 | 标题结构、封面结构、可迁移点 | 不复制原文 |
| 内容计划 | 商品 + 对标 + 模板 | 9 条内容方向 | 不生成虚假客户反馈 |
| 风险检查 | 标题、封面、正文、商品 | 红黄绿风险和改写建议 | 不声称自动合规 |

AI 的验收不是“写得像爆款”，而是：

```text
是否让用户更快做出下一步经营判断。
```

## 10. 验证通过标准

只有同时满足下面条件，才进入开发讨论：

| 标准 | 最低线 |
| --- | --- |
| 用户愿意填 | 3 个商品能完整录入，且关键字段不被认为过重 |
| 对标能找到 | 至少 2 个商品各有 3 条有效对标 |
| 内容能执行 | 至少 1 个商品的内容包被真实采用或准备发布 |
| 数据能回填 | 每天回填控制在 3 分钟左右 |
| 复盘能决策 | 至少形成 1 次放大、调整、补证据、暂停或放弃 |
| 风险能识别 | 至少识别 1 个真实发布风险 |
| 用户强匹配 | 至少 1 个强匹配用户愿意继续用或付费验证 |

如果达不到，继续改无代码表格，不进入开发。

## 11. 开发讨论入口

验证通过后，才讨论开发，并且优先级如下：

1. 内部运营工作台。
2. 商品库、对标库、内容计划、数据回填。
3. AI 辅助拆解和计划生成。
4. 规则风险提醒。
5. 再考虑用户端 SaaS。
6. 最后才考虑开放平台、服务市场或插件。

开发前仍必须确认：

- 千帆/学习中心关键规则截图。
- 商品笔记和挂车流程截图。
- 店铺分、负反馈、售后字段来源。
- 截图和订单信息脱敏方案。
- 是否只做内部使用，还是面向用户开放。

## 12. 下一轮会议只拍 3 件事

不要再泛聊功能大全。下一轮只拍：

1. 谁提供 5-10 个真实候选商品？
2. 谁负责把飞书多维表格搭出来并跑 3 个商品？
3. 谁能拿到千帆/学习中心/店铺后台关键规则截图？

这 3 件事定不下来，开发讨论没有意义。
