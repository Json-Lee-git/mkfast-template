# 小红书运营系统产品讨论工作坊指南

> 阶段：调研后的产品讨论。
> 用途：把下一轮讨论从“泛泛聊能不能做”压成一次可产出决策的工作坊。
> 边界：本次工作坊只决定验证方案，不决定开发排期，不进入代码实现。

## 1. 工作坊目标

这次会只解决一个问题：

```text
是否启动 3 个真实货源商品的无代码验证。
```

会后必须得到 6 个明确输出：

| 输出 | 最低要求 |
| --- | --- |
| 目标用户 | 第一轮到底服务谁 |
| 商品来源 | 3 个真实商品从谁的货盘里来 |
| 验证方式 | 模拟验证还是小量真实发布 |
| 执行责任 | 谁搭表、谁找对标、谁回填数据、谁核规则 |
| 时间表 | 何时开始、何时复盘 |
| 开发门槛 | 什么结果才允许进入开发讨论 |

会后如果拿不到这些输出，就视为还没讨论完。

## 2. 参会角色

| 角色 | 必须参加吗 | 负责回答的问题 |
| --- | --- | --- |
| 产品负责人 | 必须 | 系统边界、MVP、是否进入验证 |
| 运营负责人 | 必须 | 选品、内容测试、复盘动作是否真实可执行 |
| 有货源的人 | 必须 | 商品、成本、供货、发货、售后是否成立 |
| 小红书实操者 | 强烈建议 | 发布、评论、加购、店铺后台、规则截图 |
| 技术负责人 | 可旁听 | 验证通过后怎么接入当前项目，但不主导本次会 |
| 记录人 | 必须 | 记录决策、责任人、截止时间 |

技术负责人可以参加，但本次会里不要讨论数据库、路由、UI、AI 接口、支付和部署。

## 3. 会前准备

### 3.1 每个人必须读

只读这 3 份：

1. `docs/growth/xiaohongshu-ops-system-final-report.md`
2. `docs/growth/xiaohongshu-ops-system-evidence-audit.md`
3. `docs/growth/xiaohongshu-ops-system-decision-brief.md`

### 3.2 商品负责人准备

准备 5-10 个候选商品，每个商品至少有：

- 商品名称。
- 成本价。
- 预估售价。
- 毛利空间。
- 供应商或货源截图。
- 发货方式。
- 售后风险。
- 为什么觉得适合小红书。

### 3.3 运营负责人准备

每个候选商品至少准备：

- 1 条小红书对标链接或截图。
- 1 个可能的内容场景。
- 1 个可能的用户痛点。
- 1 个明显风险。

不需要准备完整内容方案，会上只决定能不能进入验证。

### 3.4 规则负责人准备

尽量准备这些截图或入口：

- 千帆商品笔记规则。
- 商品挂车流程。
- 店铺分/负反馈说明。
- 商品类目限制。
- 笔记发布相关提示。
- 学习中心或后台规则页。

如果拿不到截图，要在会上明确标记为“待核验”，不要当成已知规则。

## 4. 90 分钟议程

| 时间 | 议题 | 产出 |
| --- | --- | --- |
| 0-10 分钟 | 对齐结论 | 确认本系统不是 AI 文案工具，也不是数据平台 |
| 10-20 分钟 | 确认目标用户 | 决定第一轮服务对象 |
| 20-40 分钟 | 筛 3 个真实商品 | 从 5-10 个候选里选出 3 个 |
| 40-55 分钟 | 确认验证方式 | 模拟、小量真实发布、或二者结合 |
| 55-65 分钟 | 确认无代码表结构 | 是否按现有 8 张表跑 |
| 65-75 分钟 | 确认规则核验责任 | 谁拿后台截图，哪些规则先不碰 |
| 75-85 分钟 | 确认开发门槛 | 什么结果才进入开发讨论 |
| 85-90 分钟 | 写会议结论 | 责任人、截止时间、下次复盘时间 |

如果只有 60 分钟，砍掉技术讨论和商业化讨论，只保留商品、验证、责任人。

## 5. 会议主持脚本

### 5.1 开场

建议直接这样开：

```text
今天不讨论要不要开发，也不讨论功能大全。
今天只判断：这套小红书实物电商运营系统，是否值得用 3 个真实商品跑一轮无代码验证。
如果结论是跑，就定商品、负责人和时间。
如果结论是不跑，就写清楚为什么不跑。
```

### 5.2 防发散提醒

只要讨论跑偏到这些话题，就拉回来：

| 跑偏话题 | 拉回方式 |
| --- | --- |
| 直接做 SaaS | 先问：3 个真实商品跑过了吗？ |
| 做自动发布 | 先问：规则截图和账号风险确认了吗？ |
| 接千帆/API | 先问：无代码流程证明用户愿意填了吗？ |
| 做 AI 文案 | 先问：商品、对标、数据回填在哪？ |
| 做大品牌/代运营 | 先问：第一轮目标用户是不是已经变了？ |
| 讨论收费 | 先问：用户是否先认可系统下一步动作？ |

## 7. 商品筛选工作纸

每个候选商品填一行：

| 商品 | 成本 | 售价 | 毛利 | 供应稳定性 | 小红书场景 | 对标证据 | 风险 | 是否入选 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  | 高 / 中 / 低 |  | 有 / 无 | 高 / 中 / 低 | 是 / 否 |

优先选 3 类商品：

1. 低客单、低决策成本、内容场景明确。
2. 有情绪价值、礼物属性或生活方式表达。
3. 供应链简单、售后风险可控。

暂缓 4 类商品：

1. 强功效承诺商品。
2. 容易侵权或蹭 IP 的商品。
3. 售后复杂、退货率可能高的商品。
4. 需要强专业背书或强安全承诺的商品。

## 8. 验证启动条件

满足这些才启动：

| 条件 | 最低标准 |
| --- | --- |
| 商品 | 至少 3 个候选商品，最好 5-10 个备选 |
| 对标 | 每个入选商品至少 3 条对标线索 |
| 货源 | 成本、售价、发货、售后基本明确 |
| 账号 | 至少 1 个可用于小量测试的账号或明确先模拟 |
| 规则 | 高风险规则已经标记，不明规则有负责人核验 |
| 时间 | 7 天内有人每天回填数据 |

如果这些条件不满足，先补资料，不启动验证。

## 9. 验证通过标准

不是“爆了”才算通过。

只要满足下面 5 条，就可以进入开发讨论：

| 标准 | 判断方式 |
| --- | --- |
| 用户愿意填 | 真实使用者没有明显抵触字段和流程 |
| 对标找得到 | 至少 2 个商品能找到 3 条以上有效对标 |
| 计划可执行 | 至少 1 个商品的内容计划能直接发布或模拟执行 |
| 数据能回填 | 每日回填控制在 3 分钟左右 |
| 能形成动作 | 至少 1 次复盘给出明确下一步动作 |

如果只满足前两条，不开发，继续优化无代码模板。

## 10. 验证失败后的处理

| 失败现象 | 解释 | 下一步 |
| --- | --- | --- |
| 用户不愿意填 | 工具负担太重 | 删字段，改成陪跑表 |
| 找不到对标 | 选品方向不适合 | 换商品，不做 AI 生成 |
| 内容计划执行不了 | 方法离真实运营太远 | 先做人工陪跑 SOP |
| 数据回填太麻烦 | 留存风险高 | 降低指标数量 |
| 复盘没动作 | 系统价值不足 | 强化决策规则，暂不开发 |
| 规则不清楚 | 合规风险高 | 不真实发布，只模拟 |

失败不代表方向一定错，但代表不能进入开发。

## 11. 会后交付物

会议结束 24 小时内，必须形成：

1. 一份会议结论。
2. 3 个入选商品清单。
3. 责任人和截止时间。
4. 无代码表格链接。
5. 规则待核验清单。
6. 7 天验证排期。

建议会议结论格式：

```text
本次会议决定：
1. 第一轮目标用户是：
2. 第一轮验证商品是：
3. 原型平台是：
4. 验证方式是：
5. 规则核验负责人是：
6. 每日数据回填负责人是：
7. Day 8 复盘时间是：
8. 未满足哪些条件前，不进入开发：
```

## 12. 最终提醒

这次工作坊最重要的不是把系统讲得更完整，而是把真实验证启动起来。

如果讨论后仍然没有真实商品、负责人和时间表，就说明调研还停留在“想法成立”，没有进入“验证成立”。

当前最稳的决策仍然是：

```text
先用飞书多维表格跑 3 个真实商品；
验证用户愿不愿意填、对标找不找得到、系统能不能给下一步动作；
通过后，再讨论怎么接入当前项目。
```
